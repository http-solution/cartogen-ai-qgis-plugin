## 1. Why this document exists

`docs/OPEN_CORE_REPO_STRATEGY.md` ends with "Next steps (not done, no timeline implied)"
and `docs/IMPLEMENTATION_TRACKER.md` §1.3 marks the whole tier build-out as blocked on a
licensing decision. Both are accurate about the *Enterprise* shape of the problem. Neither
asks the narrower question this document asks:

> What is the shortest honest path from where the code actually is today to a Professional
> tier a person can pay for?

The answer, argued in §4, is shorter than either doc implies — and it does not begin with
creating the private repo.

## 3. The decision that has to come first

Two documents in `docs/` describe incompatible Professional tiers. Building either one
before choosing is how you build against an unknown target.

| | **A — Gateway as convenience** (`PRODUCT_TIERS.md`, `OPEN_CORE_REPO_STRATEGY.md`) | **B — Gateway as gate** (`TIER_RESTRUCTURE_PROPOSAL_2026-08-20.md`) |
|---|---|---|
| Community tool set | All 131 | 77 of 131 |
| Community BYOK | Yes — OpenRouter/Gemini/OpenAI/Claude | **No** — gateway or Ollama only |
| Community source | Genuinely open, GPL v2 | "Open source" branded, source **locked** |
| Pro source | n/a (Pro is a service) | **Closed** |
| What Pro sells | Convenience: no API key to manage | Access: the tools and the connectivity |
| Status | **Decided** (`OPEN_CORE_REPO_STRATEGY.md` "The decision") | **Frozen proposal, never resolved** |
| Legally coherent under GPL v2 today | **Yes** | **No** — its own §3 says so plainly |

Model B requires taking capability *away* from users who have it today, requires relicensing
or code-splitting, requires license-key validation, requires the private repo, and requires
legal counsel before any of it can start. Model A requires none of those things.

Model B is also a reversal that `TIER_RESTRUCTURE_PROPOSAL_2026-08-20.md` §3 flags against
itself: it moves direct BYOK *up* into Enterprise, so the free tier loses a capability it
ships with today. For an existing user base that is a takeaway, not an upgrade path.

**Recommendation: Model A.** Everything below assumes it. If Model B is chosen instead,
stop — this plan does not apply, and the first step becomes legal counsel, not engineering.

## 4. The central finding: the gateway needs neither the private repo nor the licensing decision

`docs/IMPLEMENTATION_TRACKER.md` §1.3 blocks "everything in that proposal's §6 engineering
build-out (the Cartogen API gateway, tier gating mechanism, closed-source packaging)" on the
licensing question. That is correct for *tier gating* and *closed-source packaging*. It is
**not** correct for the gateway, and treating them as one blocked bundle is what has kept
this stalled.

The reasoning:

1. **The gateway is a hosted service, not distributed software.** GPL v2 constrains what
   happens when you *distribute a copy* of the program. Running a LiteLLM proxy on your own
   server and selling metered access to it distributes nothing. This is precisely the
   services-based monetization `DOCUMENTATION.md` §8.1 already settled on — "paid support,
   hosting/managed deployment, a SaaS layer" — chosen specifically to remove the licensing
   question rather than resolve it.
2. **`cartogen.py` is not proprietary code and does not need to be.** It is an
   OpenAI-compatible HTTP client, structurally a sibling of `openrouter.py`. It can stay in
   the public repo under GPL v2 forever. Publishing it costs nothing: it is useless without
   a paid key, exactly as `openrouter.py` is useless without an OpenRouter key.
3. **A virtual key is not a license key.** The user pastes a `sk-...` into the same settings
   field they already use for every other provider. Auth happens at the gateway, server-side,
   where no plugin code runs and no license validation is needed. There is nothing to strip,
   compile, or obfuscate — and `docs/OPEN_CORE_REPO_STRATEGY.md` already anticipated this
   ("license validation and the gateway's own per-user auth are likely the same underlying
   system"). Under Model A they are not merely similar; the gateway's auth *is* the entire
   mechanism, and the license-key layer never needs to be built.
4. **No tier gating is added to this repo,** so `CLAUDE.md`'s prohibition is respected. A new
   provider option is not a tier check.

**Consequence:** Phases 1 and 2 below are unblocked and can start immediately. The private
repo (§Phase 3) is deferred until an Enterprise customer actually requires RBAC/SSO/M365 —
capabilities that genuinely do need separate code under separate terms.

## 6. Phase 1 — Cloud Connect Gateway MVP (the revenue path)

Goal: a person can pay, receive a key, paste it into Settings, and use Cartogen AI without
ever obtaining a provider API key.

### 6.1 Plugin side — four changes, all small

| # | Change | File | Note |
|---|---|---|---|
| 1.1 | Export `CartogenClient` | `providers/__init__.py` | Add the import and the `__all__` entry. Currently omitted deliberately; that reason expires when the gateway is live. |
| 1.2 | Construct it on `provider_name == "cartogen"` | `agent/agent.py` (the `elif` chain, lines 168–198) | Mirror the `openai` branch. |
| 1.3 | Add the `PROVIDERS` entry | `ui/settings_dialog.py` (the `PROVIDERS` list, lines 55–105) | One dict — `value: "cartogen"`, `provider_label: "Cartogen (Cloud, subscription)"`, `key_label: "Cartogen Key:"`. Place it **first** so it is the default on a fresh install. |
| 1.4 | Make `GATEWAY_BASE_URL` configurable | `providers/cartogen.py` | Currently a hardcoded placeholder (`https://gateway.cartogen.ai/v1/chat/completions`). Its own comment already flags this. Read from `QgsSettings` with the constant as default. |

Also needed: a `list_models` function for the settings dropdown, matching the
`_list_openrouter` / `_list_openai` convention. LiteLLM exposes `GET /v1/models`, so this is
a direct analogue of the existing OpenAI one.

**Deliberately not changed:** nothing is removed, gated, or restricted anywhere. Community
keeps all 131 tools and all BYOK providers.

### 6.2 Service side — deploy what already runs locally

| # | Task | Source |
|---|---|---|
| 1.5 | Register the domain, point `gateway.` at the LiteLLM container, TLS | `cartogen.py`'s placeholder assumes this hostname |
| 1.6 | Deploy LiteLLM + Postgres (the documented Docker path) | `service/README.md` "Docker path" |
| 1.7 | Replace `data/subscriptions.json` with a real database | `service/README.md` punch list item 1 |
| 1.8 | Deploy the Express site, real Stripe keys, real webhook secret | Remove the `NODE_ENV=development` signature bypass in `server.js` before this is public |
| 1.9 | Email the key instead of rendering it on the success page | punch list item 2 |
| 1.10 | Add auth to `/key-for-session` | punch list item 5 — today anyone holding a Stripe session id can read a key |

**1.8 and 1.10 are security-blocking, not polish.** The dev-mode webhook bypass means an
unauthenticated `POST /webhook` mints a free key; `server.js` guards this with
`NODE_ENV === 'development'`, so the deployment must set `NODE_ENV=production` *and* a real
`STRIPE_WEBHOOK_SECRET`. Verify both in the deployed environment, not just in `.env.example`.

### 6.3 Unit economics — check before pricing

`server.js` currently mints keys with `max_budget: 5` / `budget_duration: '30d'` against a
target price of ~$20/month (`DOCUMENTATION.md` §2.1). That implies roughly 75% gross margin
before infrastructure, which is a reasonable starting point — but the $5 figure is a
prototype default, not a modelled one. Before launch, measure actual token spend across a
representative set of real sessions (the session usage counter added in v1.2.30 makes this
measurable) and set the budget from data.

Also: map Stripe price IDs to per-plan budgets (`service/README.md` punch list item 3) and
handle `customer.subscription.updated` / `.deleted` so cancelled subscriptions actually lose
their key (item 4). Shipping without item 4 means cancellation does not revoke access.

### 6.4 Honest positioning

`DOCUMENTATION.md` §2.3 is right that everything except the gateway is already built and
already free. Pro should be sold as exactly what it is — **"skip the API key setup, get one
bill"** — and not as access to features Community already has. Overstating it invites the
comparison that undermines it, since the Community source is public and anyone can check.

## 7. Phase 2 — Production hardening (after first paying user)

- Usage dashboard for the customer (LiteLLM tracks spend per virtual key already).
- Rate-limit and abuse handling — a leaked key against a shared provider account is the main
  operational risk of this model.
- Key rotation / self-service regeneration.
- Status page and an honest failure path in the plugin when the gateway is unreachable.
  `cartogen.py`'s `complete()` already returns a structured `{"error": ...}`; confirm the
  dock widget surfaces it legibly rather than as a raw string.
- Revisit `providers/cartogen.py`'s `FALLBACK_MODELS` — `claude-default` and `gpt-default`
  are aliases defined in `litellm_config.yaml`. Model aliases must stay in sync between the
  deployed gateway config and the shipped plugin, or a plugin update silently breaks against
  an older gateway. Consider having `list_models` be the only source of truth.

## 8. Phase 3 — Private repo and Enterprise (deferred, conditional)

**Trigger:** a real Enterprise prospect requiring RBAC, SSO/SAML, private data enclaves, or
M365/SharePoint/Power BI push. Not before — `docs/OPEN_CORE_REPO_STRATEGY.md` says the same
("Create the private repo when Pro/Enterprise work actually begins — not before, since
there's nothing to put in it yet"), and Phase 1 removes the last reason to pre-empt it.

When triggered, in order:

1. Legal counsel on the private repo's license (`IMPLEMENTATION_TRACKER.md` §1.3).
2. Create the private repo; add `src/cartogen_ai/pro/` with **no** `src/cartogen_ai/__init__.py`
   (`DOCUMENTATION.md` §3.2 — adding one breaks the namespace merge for both distributions).
3. Fill in `sync-to-private.yml`'s `PRIVATE_REPO`, add `PRIVATE_REPO_DEPLOY_KEY`, remove
   `if: false`. Keep the plain `git push` — the no-force rule is a history-protection
   requirement, not a style preference.
4. Decide PyInstaller vs. Nuitka.
5. Only now does license-key validation need to exist — and only for the offline-capable
   Enterprise features, since anything gateway-mediated is already authenticated server-side.

## 9. Findings surfaced while writing this plan

### 9.1 Test baseline drift — 2 failures, not 1

`docs/BUG_TRACKER.md` states the baseline as **691 tests, 1 known failure + 6 known errors**,
and that "any different count on a full suite run is real signal to investigate."

A full run on 2026-08-21 gives **691 tests, 2 failures + 6 errors, 13 skipped**. Tool
registry confirmed at 131. The extra failure:

```
FAIL: test_result_includes_connectivity_note
      (tests.test_export_tools.TestGenerateHtmlDashboardConnectivityNote)
AssertionError: None is not true : {'error': 'folium is required for
generate_html_dashboard. Install via qpip, or in the OSGeo4W Shell: ...'}
```

**Assessment: environmental, not a code defect** — `folium` is an optional dependency
(`requirements.txt`) and is not installed in the environment this was run in. The tool
behaved correctly; it returned the documented graceful-degradation error.

**But the test itself has a real gap:** it patches `QGIS_AVAILABLE` to reach the response
dict, yet has no corresponding guard for `folium`, so it fails rather than skips when an
optional dependency is absent. Every other module in this codebase degrades gracefully
behind a guard specifically so the suite runs anywhere (`CLAUDE.md`, "Structure"). This test
does not follow that pattern.

**Recommendation:** add a `@unittest.skipUnless` guard for `folium` availability, matching
how the rest of the suite handles optional dependencies, and update the documented baseline
to state it as *1 failure + 6 errors + 1 conditional skip*. Flagged rather than applied —
per `CONTRIBUTING.md` §7.3 the fix is mechanical, but the *baseline number* is a documented
contract, and changing it should be deliberate.

### 9.2 The tracker is behind the code

`docs/IMPLEMENTATION_TRACKER.md` is stamped "against v1.2.33" while `metadata.txt` reads
`1.4.1`. The entire namespace-package restructure (`[1.4.0]`, and BUG-2026-08-21-6/-7)
landed after that stamp. For a document whose stated purpose is to be "the current, living
answer instead of making anyone cross-reference nine dated files," this is the one drift
that matters most. Folded into Phase 0.4.

### 9.3 `cartogen-ai-pro/` and `cartogen-ai-enterprise/` exist as empty directories

Beside the repo at `C:\Cartogen-AI-Core\`. Harmless, but they read as "the private repos
exist" to anyone glancing at the folder. Either remove them or drop a `README.md` in each
pointing at `docs/OPEN_CORE_REPO_STRATEGY.md` and stating they are placeholders.
