# Transparency Cards

**Audience:** procurement, compliance, and security reviewers who need to know how Cartogen AI's
higher-risk actions actually behave, without reading source code. `SECURITY.md` is the engineering
reference these cards summarize — every claim below has a corresponding file:line entry there;
nothing here is asserted that isn't already verified in that document.

**Format, modeled on ArcGIS's Trust Centre transparency-card approach** (see
`docs/SECURITY_AND_COMPETITIVE_REVIEW_2026-08.md` §B.1): what the action does, what it can't do,
who's actually in control of it, and what's been confirmed by adversarial testing rather than just
claimed.

Three cards cover the actions with the largest blast radius if something goes wrong: running
model-generated code, running model-generated SQL, and deleting/mutating existing data.

---

## Card 1 — Running model-generated Python (`execute_pyqgis_script`)

**What it does:** Lets the AI write and run a PyQGIS script directly inside the QGIS process, for
spatial operations that don't map to one of the plugin's ~130 built-in tools.

**What it can't do:**
- Import the standard library modules that provide filesystem, process, network, or system
  access outright (`os`, `subprocess`, `socket`, `sys`, `ctypes`, `pickle`, and 26 others).
- Reach those same capabilities indirectly through Qt classes that live in an otherwise-required
  module — `QFile`, `QDir`, `QProcess`, `QNetworkAccessManager`, `QSettings`, and 9 others are
  blocked by name specifically, even though the module they live in (`qgis.PyQt.QtCore`) has to
  stay importable for normal PyQGIS scripts to work at all.
- Call Python's real `eval`, `open`, `getattr`, or similar — the script's available builtins are a
  curated allowlist of roughly 50 safe names, not the real Python builtin set, so those names
  simply don't exist inside the script's scope even if the import-level check were somehow
  bypassed.

**Who's in control:** The script is generated by the AI model and runs unattended — there is no
per-script human approval step, by design (requiring one for every script would make the feature
unusable). The control here is architectural, not procedural: two independent layers (a
before-it-runs code scan, plus a restricted execution environment) rather than trusting the model
to behave.

**Confirmed by testing:** Adversarial testing found and closed four real bypasses before this card
was written — reaching a file-read primitive through `builtins`, reaching hidden object internals
through Python's string-formatting machinery, and two techniques for walking the live object graph
to find dangerous classes without importing them directly. A fifth was found in live production
use (not synthetic testing): a real agent session used an unblocked Qt class to browse the
filesystem outside the QGIS install directory before it was closed. Full exploit/fix table:
`SECURITY.md` §"Testing performed".

**Known limitation:** This is defense-in-depth against known techniques, not a formally proven
sandbox — executing attacker-influenced Python inside the host process is a fundamentally weaker
boundary than OS-level process isolation. Treat it as raising the bar significantly, not as an
absolute guarantee.

## Card 2 — Running model-generated SQL (`execute_read_only_sql`)

**What it does:** Lets the AI query a connected PostGIS database (or a virtual layer) directly with
SQL it writes itself, for analysis that's easier to express as a query than to build with the
plugin's own tools.

**What it can't do:**
- Run any statement that mutates data or schema — a keyword blocklist rejects `DROP`, `DELETE`,
  `UPDATE`, `INSERT`, `ALTER`, `CREATE`, and 15 others, plus every `;`-separated multi-statement
  query (blocking a common way to smuggle a second, disallowed statement past a naive check).
- Read arbitrary server-side files or reach a different database server through functions that
  technically aren't DML/DDL and so wouldn't be caught by a keyword list alone (`lo_export`,
  `pg_read_file`, `dblink`) — these are blocked explicitly, found during adversarial testing
  specifically because they don't look like the kind of statement a keyword blocklist expects.
- Silently run without the read-only guarantee if the database connection itself can't be
  confirmed read-only: the query is refused, not allowed through, if that confirmation fails.

**Who's in control:** Same as Card 1 — no per-query approval step. The control is a database-level
guarantee (the connection itself is set read-only, enforced by PostgreSQL, not just by the
plugin's own keyword check) layered under the keyword blocklist, so a gap in the blocklist alone
doesn't mean data can actually be changed.

**Confirmed by testing:** The `lo_export`/`pg_read_file`/`dblink` gap above was found and closed
during adversarial testing, not assumed safe from the blocklist's design. Full exploit/fix table:
`SECURITY.md` §"Testing performed".

**Known limitation:** None specific to this control beyond the general local-file-access posture
below (Card 3 covers a related but distinct action).

## Card 3 — Deleting or mutating existing data (`remove_layer`, `field_calculator`)

**What it does:** Lets the AI remove a map layer or bulk-edit an attribute field's values across
features — the two actions in the plugin that can destroy or overwrite data that already exists,
as opposed to creating something new.

**What it can't do:** Run without a human clicking a confirmation button first. The `confirmed`
flag these two actions require is stripped from any arguments the model supplies on its own — the
dispatcher's schema filtering removes it before the tool call executes, regardless of what the
model's tool-call arguments contain. The only real path to `confirmed=True` is a UI button click
in the plugin's own dock panel; there is no tool-call argument, prompt phrasing, or injected
instruction that can set it instead.

**Who's in control:** The user, explicitly, for every single destructive action — this is the one
card in this set where a human is genuinely in the loop on every occurrence, not just at a policy
level.

**Confirmed by testing:** This control is structural (argument stripping at the dispatcher level,
not a prompt instruction asking the model to ask first), so it isn't the kind of thing adversarial
prompt testing would meaningfully add to — the model literally cannot supply the flag that bypasses
it. The regression test suite (`tests/`) verifies the stripping behavior directly.

**Known limitation:** None documented for this specific control in `SECURITY.md`.

## What these cards don't cover

This is not a substitute for `SECURITY.md`, which documents the full protection set (6 additional
protections beyond the three above, the complete adversarial testing table, and every accepted-risk
limitation stated explicitly rather than left implicit). These three cards were chosen because
they're the actions with the most consequence if a control fails — read `SECURITY.md` directly for
anything not covered here, including the recurring-monitoring-scheduler and prompt-refinement-layer
protections added most recently.
