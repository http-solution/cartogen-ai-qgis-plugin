# Roadmap audit: the ten proposed features against the code (2026-10-27, build 1.18.4)

Scope: a strategic list of ten features and a competitor matrix was proposed. This audit reads the repository at `main` (1.18.4) and states, for each feature, what exists, what is partial, and what is absent, with the files and tools that prove it. It does not verify the competitor claims or the download figures in the proposal (not checked here); it audits Cartogen only. Status words: **Exists** (a tool or module does the thing end to end), **Partial** (a real foundation, a named gap), **Absent** (nothing in `src/` or `docs/`). "CI-checked" and "hand-verified" keep their meaning from `CONTRIBUTING.md`: nothing below was run in desktop QGIS by this audit.

## Findings that change the order of work

1. **Feature 1's real gap is plumbing, not a missing model ability.** The five chat clients already accept image parts; only the canvas-capture tool sends the picture the wrong way (as text in a tool result). A capture that is added as an `image_url` part of the next user message, with the legend and layer list as text beside it, would make "look at my map" work on every provider that has a vision model. Verify per provider before claiming it: this audit read the Claude conversion and the OpenAI-style request shape, not a live vision call.
2. **Feature 8 is largely assembled; what is missing is the gate.** The provenance record already carries QA-gate status and history, and the tools exist. A "verify before done" step that runs the relevant checks after an analysis (CRS, geometry validity, expected units, result range, no stale fields) and attaches the outcome to the answer is mostly orchestration plus a small set of new result checks.
3. **Features 7 and 8 and the provenance sidecar are the parts of the proposed "Verified Workflow Mode".** Its five outputs map to what exists: sources and licences (partly: provenance has lineage, licence is not recorded for fetched data), algorithms and parameters (tool lineage, yes), geometry/CRS/output checks (tools exist, not run automatically), assumptions and limitations (tools print them; no collected section), how to rerun (workflow presets, read-only steps only). The gaps are licence capture on fetch, automatic checks, and one report that gathers them.
4. **Three classes of silent wrong answer were found by hand runs, not by the model.** They are the evidence for ordering Feature 8 first: degrees treated as metres (PLAN-026 class A), a signed value ranked as if bigger meant worse (class B), stale state read as a result (class C).
5. **The competitor matrix's "not verified" cells resolve as:** multimodal screenshots Partial (finding 1); STAC discovery Exists, loading and chaining Absent; workflow replay Partial; MCP Absent; one-click undo Exists with a stated coverage list; open-data catalogue Partial (hand-picked sources, no CKAN or Copernicus); imagery extraction Exists; automated spatial QA Partial.

## Recommended order, with reasons and acceptance

| Step | Work | Why now | Acceptance (all CI-checked first, hand row after) |
|---|---|---|---|
| A | **Verified result gate** (feature 8, first slice): after each analysis tool that writes a layer or field, run the checks that apply (CRS known and projected where a distance was used; geometry valid; output field not all-null and not constant; value range plausible for the stated unit) and add `checks` to the tool result; the answer must quote a failed check | stops the class of error seen in three hand runs; reuses existing tools; no new dependency | a deliberately wrong input per check produces a failed check in the result; the three known historical defects are reproduced as tests that the gate flags |
| B | **Canvas as an image** (feature 1, first slice): a tool or button that attaches the current canvas, optionally a drawn region, plus legend text and layer list, as an `image_url` part | cheapest visible demo; no new model needed | on each provider with a vision model a live prompt "what is wrong with this map" describes the visible layers; CI covers the message shape |
| C | **Provenance and licence on fetch** (feature 5, first slice): every `fetch_*` result records source URL, licence text or identifier, date retrieved and coverage; shown before loading when large | needed by the verified-workflow report and by donors | a fetch result carries the four fields; the sidecar and `generate_report` include them |
| D | **Verified workflow report** (the proposal's lead feature): one tool that assembles A to C plus tool lineage, parameters, assumptions and the rerun recipe | the defensible differentiator; small once A to C exist | a report for one worked example (service coverage) lists every item and reruns to the same numbers |
| E | Data discovery ranking, imagery chain (STAC to change detection to validation), reports from one prompt | each builds on D | per feature |
| F | MCP transport over the existing tool registry and gates | large reach for small code, but only after A so exposed tools inherit the checks | a client cannot run a write tool without the confirmation gate |
| G | Workflow builder, multi-agent roles, cloud workers, marketplace | each needs an owner decision (tiers, security model, review process) before design | decisions recorded in `docs/IMPLEMENTATION_TRACKER.md` section 1 |
